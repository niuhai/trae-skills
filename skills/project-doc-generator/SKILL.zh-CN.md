# 项目文档生成器

## 功能概述

对项目进行全面的代码扫描，生成专业、完整、结构化的技术文档。文档内容严格基于源代码扫描结果，确保文档与代码实现的高度一致性。

## 核心原则

1. **扫描优先** - 所有文档内容必须基于实际代码扫描，不允许虚构
2. **自动检测** - 自动识别项目类型、技术栈和配置文件
3. **自适应结构** - 根据实际项目结构调整文档组织方式
4. **可视化** - 使用 ASCII 图表展示架构和流程

***

## 阶段一：项目扫描

### 1.1 基本结构扫描

```bash
# 扫描项目根目录
LS {project_path}

# 自动检测源文件类型（根据实际扩展名）
Glob {project_path}/**/*.{ts,tsx,js,jsx,vue,py,java,go,rs,php}
```

### 1.2 配置文件自动扫描

**必须自动检测并读取以下常见配置文件（根据实际存在性）：**

| 类别 | 配置文件 | 说明 |
|------|----------|------|
| Node/前端 | `package.json`, `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock` | 依赖项和技术栈 |
| 构建配置 | `vite.config.ts`, `vite.config.js`, `webpack.config.js`, `rollup.config.js`, `next.config.js`, `nuxt.config.ts`, `react.config.js` | 构建工具配置 |
| TypeScript | `tsconfig.json`, `jsconfig.json` | TypeScript 配置 |
| 代码规范 | `.eslintrc.js`, `.eslintrc.json`, `.eslintrc.cjs`, `.prettierrc`, `.prettierrc.json` | 代码规范配置 |
| 环境配置 | `.env`, `.env.local`, `.env.development`, `.env.production`, `.env.test` | 环境变量配置 |
| Python | `requirements.txt`, `Pipfile`, `pyproject.toml`, `setup.py` | Python 依赖 |
| Java | `pom.xml`, `build.gradle`, `build.gradle.kts` | Java 构建配置 |
| Go | `go.mod`, `go.sum` | Go 模块配置 |
| Rust | `Cargo.toml`, `Cargo.lock` | Rust 包管理 |
| PHP | `composer.json` | PHP 依赖 |
| .NET | `*.csproj`, `*.sln` | .NET 项目文件 |
| 数据库 | `db.config.js`, `database.yml`, `prisma.schema` | 数据库配置 |

## 阶段二：文档结构规划

### 2.1 目录结构模板

```
{project_path}/项目文档/
├── 01-项目概述/
│   └── 项目概述.md
├── 02-技术架构/
│   └── 技术架构.md
├── 03-{业务模块A}/
│   └── {业务模块A}.md
├── 04-{业务模块B}/
│   └── {业务模块B}.md
├── ...
├── 0N-{最后业务模块}/
│   └── {最后业务模块}.md
├── 0N+1-API接口规范/
│   └── API接口规范.md
├── 0N+2-数据模型/
│   └── 数据模型.md
├── 0N+3-核心业务逻辑/
│   └── 核心业务逻辑.md
└── 0N+4-部署配置/
    └── 部署配置.md
```

### 2.2 业务模块识别规则

- `src/` 或对应源码目录下每个一级目录 = 一个业务模块
- 如果存在 `pages/` 或 `views/`，其中的每个一级子目录 = 一个业务模块
- 模块名称使用中文，格式：`{序号}-{模块中文名称}`
- 特殊情况：包含多个子模块的目录需要进一步细分

## 阶段五：执行流程

### 步骤一：自动扫描项目

1. `LS {project_path}` - 查看项目结构
2. `Glob **/*` - 获取所有文件（不限扩展名）
3. 自动识别项目类型（前端/后端/全栈）
4. 自动检测存在的配置文件

### 步骤二：分析模块

1. 扫描源码目录确定业务模块数量和名称
2. 扫描 API/接口目录确定接口结构
3. 扫描类型/模型定义确定数据模型
4. 扫描配置文件确定枚举和常量

### 步骤三：创建目录

```bash
mkdir "项目文档/01-项目概述"
mkdir "项目文档/02-技术架构"
mkdir "项目文档/03-{模块1}"
# ... 根据实际业务模块创建
mkdir "项目文档/0N-API接口规范"
mkdir "项目文档/0N+1-数据模型"
mkdir "项目文档/0N+2-核心业务逻辑"
mkdir "项目文档/0N+3-部署配置"
````

### 步骤四：生成文档

使用子代理并行生成模块文档：

- 每个模块是独立的 md 文件
- 严格遵循模板结构
- 包含 ASCII 图表
- 基于实际扫描的代码

***

## 质量标准

1. **准确性** - 文档内容必须与代码严格保持一致
2. **完整性** - 每个模块必须包含：介绍、文件、组件/类、接口/函数、枚举/常量、流程图
3. **可读性** - 语言精准、逻辑清晰、结构合理
4. **可视化** - 关键流程必须包含 ASCII 图表
5. **自适应性** - 根据实际项目类型调整文档内容，不假设特定技术栈

***

## 输出

在 `{project_path}/项目文档/` 目录下生成：

1. **项目概述.md** - 项目背景、技术栈、架构图
2. **技术架构.md** - 目录结构、架构分层
3. **{业务模块N}.md** - 各业务模块详细文档
4. **API接口规范.md** - HTTP封装、拦截器、认证
5. **数据模型.md** - 类型定义、枚举
6. **核心业务逻辑.md** - 核心算法、流程
7. **部署配置.md** - 环境变量、构建命令
